Hackathon submission: "Voice-Dispatched Hotel Service Robot," AssemblyAI
Voice Agent Hackathon on lablab.ai. Full narrative plan in `PLAN.md`,
technical detail in `ARCHITECTURE.md`, hard constraints (read before writing
any code) in `CLAUDE.md`. Three real processes: an orchestrator (AssemblyAI

physics per robot), and an admin API + dashboard (FastAPI + Next.js). All
three talk to one shared Supabase project.

### The bug chain in this strand (read this before touching `nav.py` or `engine.py`)

All of these were found with real physics evidence, never guessed — this
project's established convention, keep following it:

1. **Task 1**: this machine's `mj_step` realtime pacing runs at ~70-80% of
   wall-clock — never trust `time.sleep(N)` as "N seconds of simulated
   motion" anywhere in this codebase; poll real position/state instead.
   Also: MuJoCo's `mode="track"` camera keeps orientation fixed in the world
   frame (position-only tracking) — use `mode="fixed"` for a camera that
   should track both position and orientation.
2. **Task 2, round 1**: `pure_pursuit_step` originally dead-reckoned
   (`progress_m + speed_mps * dt`). Combined with #1's slower-than-wall-clock
   physics, this drifted the estimate ahead of the robot's real position and
   clipped corners. Fixed by deriving `progress_m` from the robot's real
   measured position every call (nearest point on the path polyline →
   arc-length), dropping `dt` entirely.
3. **Task 2, round 1 (same fix)**: reading `sim.data.contact`/`sim.data.ncon`
   directly (for a wall-contact regression test) without `sim._lock` races
   the background `mj_step` thread and throws a real `IndexError`. Fixed by
   snapshotting `(geom1, geom2)` pairs under the lock before resolving names.
   **This pattern generalizes**: anything reading `sim.data`/`sim.model`
   directly (not through `pull_status()`) needs the same care.
4. **Task 2, round 2 — found by Task 3, after Task 2 had already been
   reviewed and approved.** The fix in #2 added `new_progress_m =
   max(progress_m, measured_s)`, defensively "never regressing from a noisy
   projection" — reasonable-sounding, never actually exercised by Task 2's
   own tests, and it turned out to be wrong: on the REVERSED path
   `_drive_home` feeds this function for a recall/return trip, a robot close
   to the reversed path's end genuinely needs `measured_s` to *decrease* for
   a while as it completes a real course-reversal U-turn (`sim.drive` always
   commands forward `v`, so reversing direction traces a wide loop, not an
   instant pivot). The floor clamped that legitimate regression at its
   highest-ever value, permanently freezing the lookahead — the robot never
   turned around. **Fixed by dropping the floor entirely**:
   `new_progress_m` is now always the fresh `_closest_arc_length` result, no
   memory of past calls. This also makes every `progress_m = 0.0` reset
   in `engine.py` unnecessary (harmless, but pointless) — removed those too.
   A permanent regression test was added to `nav.py`'s own self-check for
   exactly this shape of bug (drive partway, hand `pure_pursuit_step` the
   same path reversed with the stale progress value carried through unreset,
   confirm it still arrives).
5. **A related, non-bug finding worth knowing**: a recall very close to the
   desk requires the robot to complete close to a 180-degree turn while
   already near its target. This is genuinely *slow* to converge under the
   `omega = steer_gain * heading_error` proportional steering law (near-180
   degree error is the textbook slow case for this kind of controller, and
   the real force-controlled actuators don't reach commanded angular
   velocity instantly) — traced tick-by-tick and confirmed it's monotonic
   convergence, not a stall, just needs a generous tick budget. Do not
   "fix" this as if it were a bug; it isn't one. Tune tick budgets with real
   measurements the way every self-check in this codebase already does,
   never guess.
