### Real bugs found and fixed in this strand (all via genuine physics evidence, not guesswork — important context for anyone continuing)

1. **Task 1's camera plan defect** (caught before dispatch): the original
   plan step told an implementer to "eyeball a live viewer window" —
   impossible for an unattended subagent. Fixed to offscreen-render via
   `mujoco.Renderer` to PNGs and actually Read/inspect them.
2. **Task 1 implementation, 3 real deviations found by the implementer**,
   all independently re-verified by the reviewer: (a) this machine's
   `mj_step` realtime-pacing loop runs at ~70-80% of wall-clock speed —
   `time.sleep(N)` in any script does NOT mean N seconds of simulated
   motion; poll real position/state instead of trusting elapsed wall-clock
   time, everywhere in this codebase, on this machine; (b) turning at the
   junction too early clips the inside corner of the L — must drive to
   the far arm's own centerline before turning; (c) MuJoCo's
   `mode="track"` camera keeps *orientation* fixed in the world frame
   (only position translates, it does NOT rotate with the body) — use
   `mode="fixed"` (rigid attachment) instead for a camera that should
   track both position and orientation.
3. **Task 2's real design bug, found by the implementer, ruled a plan
   defect by the controller, and fixed via a full plan-doc rewrite +
   implementer resume**: `pure_pursuit_step` originally dead-reckoned
   `progress_m` via `speed_mps * dt`. Combined with finding #2(a) above
   (slower-than-wall-clock physics), a fixed nominal `dt` drifts the
   dead-reckoned estimate ahead of the robot's real position, pulling the
   pure-pursuit lookahead onto the *next* leg of the path while the robot
   is still physically inside the previous corridor segment — clips a
   wall at any corner. **Fixed by redesigning `pure_pursuit_step` to
   derive `progress_m` from the robot's real measured position every call**
   (nearest point on the path polyline → arc length), which drops the `dt`
   parameter entirely and also retired a since-obsolete "re-anchor"
   formula for direction reversals (now just resets `progress_m = 0.0`,
   which is now provably correct rather than merely convenient).
4. **A fourth bug, found by the implementer while re-verifying bug #3's
   fix**: reading `sim.data.contact`/`sim.data.ncon` directly (for the new
   wall-contact regression test) without holding `sim._lock` races the
   background `mj_step` thread's array resize and can throw a real
   `IndexError`. Fixed by snapshotting `(geom1, geom2)` pairs under the
   lock before resolving names via `mujoco.mj_id2name`. **Flag for any
   future task**: anything reading `sim.data`/`sim.model` directly (not
   through the already-lock-safe `pull_status()`) needs the same care —
   nothing currently enforces this pattern outside `pull_status()` itself.

**Net effect for continuation**: `nav.py`'s pure_pursuit_step signature is
now `pure_pursuit_step(sim, path, progress_m, speed_mps, lookahead_m=0.15,
arrival_tolerance_m=0.05, steer_gain=2.0) -> (new_progress_m, frac, done)`
— **no `dt` parameter**. Task 3's plan text (engine.py integration) was
already updated to match this corrected signature before Task 2 was even
re-dispatched, so the plan document itself should be internally consistent
already — but confirm by reading it fresh rather than trusting this
summary, since the plan file has been the site of two defect-fix rewrites
already and could in principle need a third if Task 2's pending review
surfaces anything else.
